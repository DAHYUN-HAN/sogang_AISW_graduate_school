# 원우회비 납부 범위와 활동 인증 참가자 검색 설계

## 1. 목표

활동 인증 참가자 검색 대상을 원우회비 납부자에서 전체 원우로 넓힌다. 검색 결과에서는 현재 활동 인증 게시판 기준으로 회비 효력이 있는 원우를 검정색, 효력이 없는 원우를 회색으로만 구분한다. 회비 미납 여부는 참가자 선택이나 활동 인증 저장을 막지 않는다.

관리자는 기존 원우회비 관리 화면에서 다음 세 가지 상태를 관리한다.

- `ALL`: 전체 납부. 모든 활동 인증 게시판에서 납부자로 취급한다.
- `ONCE`: 특정 행사 1회 납부. 지정한 활동 인증 게시판에서만 납부자로 취급한다.
- `UNPAID`: 미납. 어떤 활동 인증 게시판에서도 납부자로 취급하지 않는다.

한 원우는 동시에 하나의 상태만 가진다. `ONCE`는 한 번에 하나의 게시판만 지정할 수 있다.

## 2. 현재 구조와 변경 원칙

현재 `dues_payers`는 학번, 이름, 전공만 저장하며 행의 존재 자체가 납부를 뜻한다. 이 구조로는 미납 원우를 검색할 수 없고 특정 행사 납부도 표현할 수 없다.

이번 변경에서는 별도 납부 권한 테이블을 만들지 않는다. 기존 `dues_payers`를 전체 원우 명부와 회비 상태를 함께 담는 단일 테이블로 확장한다. 기존 테이블명과 API 경로는 호환성을 위해 유지하되, 문서와 관리자 UI에서는 이 데이터를 “원우 명부/회비 상태”로 설명한다.

`users`는 학번을 저장하지 않고 앱 미가입 원우도 존재할 수 있으므로 전체 원우 명부의 원천으로 사용하지 않는다. 관리자가 별도의 전체 원우 명부 XLSX를 먼저 반영하고, 원우회비 납부 XLSX는 그 명부와 대조하여 상태만 갱신한다.

## 3. 데이터 모델

`dues_payers`에 다음 컬럼을 추가한다.

| 컬럼 | 타입 | 규칙 |
| --- | --- | --- |
| `is_full_paid` | `BOOLEAN NOT NULL DEFAULT FALSE` | `ALL` 상태이면 `TRUE` |
| `once_board_id` | `INTEGER NULL` | `boards.id` 외래 키, `ON DELETE SET NULL` |

다음 데이터베이스 제약을 둔다.

- `is_full_paid = TRUE`와 `once_board_id IS NOT NULL`은 동시에 허용하지 않는다.
- `once_board_id`에는 조회 성능을 위한 인덱스를 둔다.
- 관리자 API에서 `once_board_id`는 활성 상태의 `activity_certification` 게시판만 허용한다. 다른 게시판, 비활성 게시판, 존재하지 않는 게시판은 `422 INVALID_DUES_BOARD`로 거절한다.

상태는 두 컬럼에서 다음과 같이 계산한다.

| `is_full_paid` | `once_board_id` | 상태 |
| --- | --- | --- |
| `TRUE` | `NULL` | `ALL` |
| `FALSE` | 값 있음 | `ONCE` |
| `FALSE` | `NULL` | `UNPAID` |

현재 활동 인증 게시판 `B`에서의 납부 효력은 다음 식 하나로 계산한다.

```text
is_paid_for_board = is_full_paid OR once_board_id = B.id
```

게시판 이름은 저장하지 않는다. 관리자 응답과 UI에서 `boards.name`을 조인해 표시하므로 게시판 이름을 바꿔도 납부 연결이 깨지지 않는다. 연결된 게시판이 삭제되면 `once_board_id`가 `NULL`이 되어 해당 원우는 `UNPAID`가 된다.

### 마이그레이션

Alembic 마이그레이션은 새 컬럼, 외래 키, 체크 제약, 인덱스를 추가한다. 기존 `dues_payers` 행은 지금까지 전체 납부자로 사용됐으므로 `is_full_paid = TRUE`, `once_board_id = NULL`로 백필해 배포 직후 기존 동작을 보존한다.

## 4. 명부와 납부 XLSX 처리

전체 원우 검색을 위해 관리 화면에 서로 목적이 다른 두 업로드를 둔다. 두 파일 모두 첫 시트, 헤더 없음, `이름 / 전공 / 학번` 세 열 형식을 사용하며 기존 행 단위 검증과 전체 트랜잭션 원칙을 유지한다.

### 4.1 전체 원우 명부 업로드

`POST /dues-payers/admin/roster/import`

- 정규화한 학번을 키로 이름과 전공을 생성 또는 갱신한다.
- 기존 `is_full_paid`와 `once_board_id`는 변경하지 않는다.
- 파일에 빠진 기존 행을 삭제하거나 비활성화하지 않는다. 기존 활동 인증의 참가자 ID와 이력 보존이 우선이다.
- 결과는 `{created, updated, unchanged, total_rows}`를 반환한다.

### 4.2 전체 납부자 스냅샷 업로드

기존 `POST /dues-payers/admin/import`를 원우회비 전체 납부자 스냅샷 업로드로 정의한다.

1. 파일 전체를 먼저 검증한다.
2. 각 행을 정규화 학번과 앞뒤 공백을 제거한 정확한 이름 조합으로 전체 원우 명부와 대조한다. 전공은 매칭 키가 아니다.
3. 한 행이라도 명부에 없거나 학번은 같지만 이름이 다르면 `422 DUES_IMPORT_ROSTER_MISMATCH`로 전체 업로드를 거절한다. 이때 기존 상태는 전혀 바꾸지 않는다.
4. 모든 행이 매칭되면 트랜잭션 안에서 기존 `is_full_paid = TRUE`를 모두 `FALSE`로 초기화한다.
5. 업로드에 포함된 원우를 `is_full_paid = TRUE`, `once_board_id = NULL`로 바꾼다. 기존 `ONCE` 원우가 전체 납부 목록에 들어오면 `ALL`로 승격된다.
6. 업로드에 포함되지 않은 `ONCE` 상태는 유지한다. 이전 `ALL`이면서 이번 파일에 없는 원우는 `UNPAID`가 된다.

결과는 `{activated, reset, unchanged, total_rows}`를 반환한다. `activated`는 기존 `UNPAID` 또는 `ONCE`에서 `ALL`이 된 수, `reset`은 기존 `ALL`이었지만 이번 파일에 없어 `UNPAID`가 된 수, `unchanged`는 기존에도 `ALL`이고 이번 파일에도 포함된 수다. 따라서 `activated + unchanged = total_rows`다. 성공 감사 로그에는 이 건수들만 기록하고 이름·학번은 넣지 않으며, 실패 응답은 PII 없이 오류 코드와 행 번호만 반환한다.

배포 운영 순서는 전체 원우 명부 업로드 후 전체 납부자 스냅샷 업로드다.

## 5. 관리자 개별 관리 API와 화면

다음 관리자 전용 API를 추가한다.

- `POST /dues-payers/admin/payers`: 원우 한 명 생성
- `PUT /dues-payers/admin/payers/{payer_id}`: 인적 정보와 회비 상태 수정

요청 형식은 다음과 같다.

```json
{
  "name": "홍길동",
  "major": "인공지능",
  "student_number": "A74001",
  "payment_scope": "ONCE",
  "once_board_id": 12
}
```

검증 규칙은 다음과 같다.

- `ALL`과 `UNPAID`는 `once_board_id`를 허용하지 않는다.
- `ONCE`는 유효한 `once_board_id`를 반드시 요구한다.
- 학번은 기존 형식 `A`와 숫자 5자리로 정규화하며 중복을 허용하지 않는다.
- 신규 원우도 `UNPAID`로 등록할 수 있어, XLSX에 반영하기 전 긴급한 명부 보완이 가능하다.

관리자 목록 응답은 기존 기본 필드에 `payment_scope`, `is_full_paid`, `once_board_id`, `once_board_name`을 추가한다. 화면은 상태 배지와 특정 게시판 이름을 표시하고 생성/수정 폼에서 `전체 납부`, `특정 행사 1회 납부`, `미납` 중 하나를 선택하게 한다. `ONCE`를 선택한 경우에만 활성 활동 인증 게시판 선택기를 노출한다.

기존 영구 전체 삭제 기능은 원우 명부와 회비 상태를 함께 지우는 동작으로 유지하고, 경고 문구에 그 범위를 명시한다.

## 6. 활동 인증 참가자 검색과 저장

`GET /dues-payers/search`는 `q`, `size`와 함께 현재 `board_id`를 필수로 받는다.

- `board_id`는 활성 `activity_certification` 게시판이어야 한다.
- 이름 검색은 `dues_payers`의 모든 행을 대상으로 한다. `UNPAID`와 다른 게시판의 `ONCE`도 검색 결과에 포함한다.
- 학번 검색은 현재 개인정보 보호 규칙대로 허용하지 않는다.
- 회원 응답은 `{id, name, major, student_number, is_paid_for_board}`만 반환한다. 다른 게시판의 1회 납부 대상이나 전체 상태 원문은 노출하지 않는다.

활동 인증 작성/수정 화면은 검색 결과의 이름과 전공을 다음 두 색상으로만 표시한다.

- `is_paid_for_board = true`: 검정
- `is_paid_for_board = false`: 회색

주황색 1회 납부 표시는 제거한다. `ONCE`가 현재 게시판과 일치하면 검정, 다른 게시판을 가리키면 회색이다. 두 상태 모두 선택할 수 있고 참가자 칩에도 별도의 차단 상태를 두지 않는다. 하단 안내 문구도 검정은 현재 활동 기준 납부, 회색은 현재 활동 기준 미납이라는 두 상태만 설명한다.

활동 인증 게시글 저장 규칙은 납부 효력을 권한 조건으로 사용하지 않는다. `metadata.participant_dues_payer_ids`가 전체 원우 명부에 존재하는지만 검증하고, 서버가 `metadata.participants` 이름 스냅샷을 다시 만든다. 따라서 미납 원우도 정상적으로 참가자로 저장되며, 이후 회비 상태나 이름이 바뀌어도 과거 게시글의 이름 스냅샷은 유지된다.

## 7. 오류 처리와 원자성

- XLSX 파싱·행 검증·명부 매칭이 끝나기 전에는 어떤 상태도 갱신하지 않는다.
- 전체 납부 스냅샷 초기화와 새 납부자 반영은 한 트랜잭션에서 처리한다.
- 관리자 개별 수정에서 게시판 검증이 실패하면 기존 상태를 유지한다.
- 활동 인증 검색에 잘못된 게시판 ID가 오면 `422 INVALID_DUES_BOARD`를 반환한다.
- 활동 인증 게시글 저장은 회비 상태가 아니라 명부 존재 여부만 검사하므로 기존 `INVALID_DUES_PAYER` 의미를 유지한다.

## 8. 테스트 범위

### 필수 인수 시나리오

1. **관리자 전체 납부 일괄 등록**
   - 관리자가 먼저 전체 원우 명부 XLSX를 업로드한다.
   - 이어서 원우회비 전체 납부자 XLSX를 업로드한다.
   - 업로드 직전의 모든 `ALL`을 초기화한 뒤, 파일에서 학번과 이름이 모두 일치한 원우만 `ALL`이 된다.
   - 파일에 없는 기존 `ALL`은 `UNPAID`가 되고, 파일에 없는 기존 `ONCE`는 해당 게시판 전용 상태를 유지한다.
   - 명부 불일치가 한 건이라도 있으면 전체 업로드가 실패하고 기존 상태가 그대로 남는지 확인한다.

2. **관리자 게시판 전용 납부 적용**
   - 관리자가 원우회비 목록에서 원우를 신규 등록하거나 기존 원우를 수정한다.
   - 상태를 `특정 행사 1회 납부(ONCE)`로 선택하고 활성 활동 인증 게시판 하나를 지정한다.
   - 저장 후 관리자 목록에 `ONCE`와 지정 게시판 이름이 함께 표시되는지 확인한다.
   - `ONCE` 원우가 이후 전체 납부자 XLSX에 포함되면 `ALL`로 전환되고 게시판 전용 연결은 제거되는지 확인한다.

3. **활동 인증 검색 색상 적용**
   - 활동 인증 게시판 A의 작성 및 수정 화면에서 이름으로 참가자를 검색한다.
   - `ALL`은 검정, 게시판 A를 지정한 `ONCE`도 검정으로 표시한다.
   - `UNPAID`는 회색, 다른 게시판 B를 지정한 `ONCE`도 회색으로 표시한다.
   - 검색 결과와 안내 문구에 주황색 상태가 남아 있지 않은지 확인한다.
   - 검정과 회색 참가자 모두 선택·제출 가능하고, 저장된 활동 인증에 참가자 이름이 정상 노출되는지 확인한다.

### 백엔드

- 마이그레이션 컬럼, 외래 키, 체크 제약, 인덱스와 기존 행 `ALL` 백필
- 전체 명부 XLSX 생성/갱신 및 회비 상태 보존
- 납부 XLSX의 전체 초기화, 정확한 이름·학번 매칭, `ONCE` 보존, `ONCE`에서 `ALL` 승격
- 매칭 실패 시 전건 롤백
- 관리자 개별 `ALL`/`ONCE`/`UNPAID` 생성·수정과 잘못된 게시판 거절
- 활동 게시판별 `is_paid_for_board` 계산
- 미납 원우 검색·선택·활동 인증 저장 허용
- 비관리자의 관리자 API 접근 거절과 감사 로그의 PII 미포함

### 프론트엔드

- 관리자 상태 표시, 개별 등록/수정, 두 XLSX 업로드 요약
- 활동 인증 검색 요청의 `board_id` 전달
- `ALL`, 일치하는 `ONCE`는 검정, `UNPAID`와 불일치 `ONCE`는 회색
- 주황색 상태와 기존 3색 안내 문구 제거
- 미납 검색 결과도 선택 및 제출 가능
- 기존 참가자 이름 스냅샷 편집 호환성 유지

전체 백엔드 테스트, 프론트엔드 테스트, 프론트엔드 타입 검사를 완료 조건으로 삼는다.

## 9. 범위 제외

- 한 원우에게 여러 개의 `ONCE` 게시판을 동시에 부여하는 기능
- 회비 결제 내역, 금액, 결제일, 환불 이력 관리
- 앱 회원 계정과 원우 명부의 자동 연결
- 회비 상태에 따른 활동 인증 작성/참가자 선택 차단
- 과거 활동 인증의 이름 스냅샷 일괄 재작성
