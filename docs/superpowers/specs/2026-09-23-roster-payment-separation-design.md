# 원우 명부와 현재 학기 원우회비 분리 설계

작성일: 2026-09-23
대상 작업: Phase 4 관리자·활동인증 P0 보정
상태: 사용자 검토 대기

## 1. 목적

전체 원우 명부와 현재 학기 원우회비 납부 상태의 수명주기가 다르므로 저장소와 관리자 화면을 분리한다.

- 전체 원우 명부는 학교를 거쳐 간 원우의 영구 신원 기록이다. 명부 업로드는 기존 행을 삭제하지 않는다.
- 원우회비 정보는 현재 학기 스냅샷이다. 새 납부자 엑셀을 업로드하면 이전 납부 정보 전체를 교체한다.
- 활동인증 참가자 검색은 전체 원우 명부를 대상으로 하며, 현재 학기 납부 정보는 검정·회색 표시만 결정한다.
- 납부 여부와 무관하게 모든 명부 행은 참가자로 선택할 수 있다.

## 2. 검토한 접근

### A. 명부 테이블과 현재 납부 테이블 분리 — 채택

영구 명부와 교체 가능한 납부 스냅샷을 별도 테이블로 관리한다. 명부 ID를 납부 행과 활동인증 참가자 메타데이터의 안정적인 식별자로 사용한다.

장점:

- 엑셀 업로드로 납부 테이블 전체를 교체해도 명부와 과거 활동인증 참가자 연결이 유지된다.
- 원우 명부 화면에서 납부 개념을 완전히 숨길 수 있다.
- `UNPAID`를 납부 행 부재로 표현해 저장 의미가 명확하다.

단점:

- Alembic 데이터 이관과 조인 로직 변경이 필요하다.

### B. 기존 단일 테이블 유지

`dues_payers`의 납부 컬럼만 업로드마다 초기화한다.

기각 이유: 영구 신원과 학기별 상태가 한 행에 계속 결합되고, 원우 명부와 납부 관리의 책임 분리가 DB 수준에서 성립하지 않는다.

### C. 학기 이력형 납부 테이블

학기 코드를 두고 모든 학기의 납부 이력을 보존한다.

기각 이유: 현재 요구사항은 업로드할 때 현재 납부 테이블을 새로 시작하는 방식이며 과거 학기 조회·복원은 범위에 없다. 필요해지면 별도 후속 작업으로 설계한다.

## 3. 데이터 모델

### `student_roster`

기존 `dues_payers`의 신원 데이터를 보존하면서 테이블을 영구 명부 의미로 전환한다.

- `id INTEGER PRIMARY KEY`
- `student_number VARCHAR(20) NOT NULL UNIQUE`
- `name VARCHAR(50) NOT NULL`
- `major VARCHAR(100) NOT NULL`
- `created_at DATETIME NOT NULL`
- `updated_at DATETIME NOT NULL`
- 이름, 학번, 전공 검색을 위한 인덱스

`is_full_paid`와 `once_board_id`는 이 테이블에서 제거한다. 회원 계정인 `users`와는 계속 독립적이다.

### `dues_payments`

현재 학기 납부자만 저장한다.

- `id INTEGER PRIMARY KEY`
- `roster_member_id INTEGER NOT NULL UNIQUE REFERENCES student_roster(id) ON DELETE CASCADE`
- `scope VARCHAR(10) NOT NULL`, 허용값 `ALL`, `ONCE`
- `once_board_id INTEGER NULL REFERENCES boards(id) ON DELETE CASCADE`
- `created_at DATETIME NOT NULL`
- `updated_at DATETIME NOT NULL`

제약조건:

- `ALL`이면 `once_board_id IS NULL`
- `ONCE`이면 `once_board_id IS NOT NULL`
- 원우 한 명당 현재 납부 행은 최대 하나
- `ONCE` 대상은 활성 `activity_certification` 게시판만 API에서 허용

`UNPAID`는 `dues_payments` 행이 없는 상태다. `ONCE` 게시판이 삭제되면 해당 납부 행도 삭제되어 자동으로 `UNPAID`가 된다.

학기 컬럼과 과거 납부 이력은 저장하지 않는다. 가장 최근 성공한 엑셀 업로드와 이후 개별 수정이 현재 상태의 전부다. 업로드·수정 주체와 결과 건수는 기존 운영 감사 로그에 PII 없이 기록한다.

## 4. 마이그레이션

새 Alembic 리비전은 다음 순서로 실행한다.

1. `student_roster`와 `dues_payments` 목표 구조를 만든다.
2. 기존 `dues_payers`의 모든 신원 행을 같은 `id`로 `student_roster`에 복사한다.
3. `is_full_paid = true` 행은 `ALL` 납부 행으로 복사한다.
4. `is_full_paid = false`이고 `once_board_id IS NOT NULL`인 행은 `ONCE` 납부 행으로 복사한다.
5. 기존 활동인증 `participant_dues_payer_ids`는 ID가 유지되므로 값 변경 없이 `student_roster.id`로 해석한다.
6. 데이터 건수와 제약조건을 확인한 뒤 기존 `dues_payers`를 제거한다.

다운그레이드는 두 테이블을 다시 단일 `dues_payers` 구조로 합친다. 운영 데이터에 대해 신원 행 수, `ALL` 수, `ONCE` 수가 왕복 전후 일치해야 한다.

## 5. 업로드와 수정 규칙

### 전체 원우 명부 업로드

입력은 기존과 같은 헤더 없는 `이름 / 전공 / 학번` 3열 `.xlsx`다.

- 같은 학번이 없으면 새 명부 행을 삽입한다.
- 같은 학번이 있으면 이름과 전공을 overwrite한다.
- 엑셀에서 빠진 기존 명부 행은 유지한다.
- 기존 납부 행은 변경하지 않는다.
- 파일 내부 학번 중복, 빈 값, 학번 형식 오류는 전체 업로드를 원자적으로 거절한다.
- 결과는 `created`, `updated`, `unchanged`, `total_rows` 건수를 반환한다.

### 전체 원우회비 납부자 업로드

입력은 헤더 없는 `이름 / 전공 / 학번` 3열 `.xlsx`다. 전공은 파일 형식을 맞추기 위해 받지만 명부 매칭은 정규화한 학번과 정확한 이름으로 검증한다.

1. 모든 행이 `student_roster`와 일치하는지 먼저 검증한다.
2. 한 행이라도 불일치하면 기존 납부 테이블을 변경하지 않고 전체 요청을 거절한다.
3. 검증이 끝나면 기존 `dues_payments` 행을 전부 삭제한다. 기존 `ALL`과 관리자가 지정한 `ONCE`가 모두 초기화된다.
4. 업로드 행마다 `ALL` 납부 행을 생성한다.
5. 전체 교체와 감사 로그는 하나의 트랜잭션으로 커밋한다.

### 개별 납부 수정

관리자는 명부 원우를 검색해 다음 중 하나로 변경한다.

- `ALL`: 납부 행을 생성하거나 `ALL`로 갱신하고 게시판 연결을 제거한다.
- `ONCE`: 납부 행을 생성하거나 `ONCE`로 갱신하고 선택한 활동인증 게시판을 연결한다.
- `UNPAID`: 납부 행을 삭제한다.

이 화면에서는 이름, 학번, 전공을 수정할 수 없다. 모든 명부·납부 mutation은 기존 PostgreSQL advisory lock을 공유해 업로드와 개별 수정이 동시에 섞이지 않게 한다.

## 6. API 계약

기존 `/api/dues-payers` 루트는 앱 호환성을 위해 유지하되 관리자 경로의 책임을 명확히 분리한다.

- `GET /api/dues-payers/search`
  - 인증 사용자
  - 전체 명부를 이름으로 검색
  - 납부 테이블을 조인해 요청 게시판 기준 `is_paid_for_board`만 추가
- `GET /api/dues-payers/admin/roster`
  - 관리자
  - 이름·학번·전공 통합 검색과 페이지네이션
  - 응답에 납부 필드를 포함하지 않음
- `POST /api/dues-payers/admin/roster/import`
  - 관리자
  - 명부 upsert
- `GET /api/dues-payers/admin/payments`
  - 관리자
  - 명부와 현재 납부 상태를 조인해 검색·페이지네이션
- `POST /api/dues-payers/admin/payments/import`
  - 관리자
  - 현재 납부 테이블 전체 교체
- `PUT /api/dues-payers/admin/payments/{roster_member_id}`
  - 관리자
  - `ALL`, `ONCE`, `UNPAID` 지정

기존 임시 경로 `/admin/payers`, `/admin/import`, `/admin/payments/reset`은 프론트엔드 전환과 함께 제거한다. 별도 초기화 API와 UI는 전체 납부자 업로드 자체가 전체 초기화이므로 제거한다.

모든 성공·오류 응답은 현재의 `{status, data}` 및 `{status, message, code}` 형식을 유지한다.

## 7. 관리자 화면

관리자 기본 메뉴에 별도 상위 항목 두 개를 둔다.

### `원우 명부`

- 전체 원우 명부 업로드
- 이름·학번·전공 통합 검색
- 총 인원 표시
- 한 페이지 100명
- 밀도 높은 테이블: `이름 | 학번 | 전공`
- 넓은 화면에서는 고정 열 폭과 헤더를 사용하고, 좁은 화면에서도 같은 세 열을 가로 스크롤로 유지한다.
- 납부 상태, 게시판, 납부 수정, 개별 명부 수정 UI를 노출하지 않는다.

### `원우회비`

- 현재 학기 전체 납부자 엑셀 업로드
- 업로드가 기존 `ALL`과 `ONCE`를 모두 초기화한다는 경고 및 확인
- 이름·학번·전공 검색
- 목록에서 신원은 읽기 전용으로 표시
- 상태는 `전체 납부`, `특정 행사 1회 납부`, `미납`으로 표시
- 행별 수정으로 `ALL`, `ONCE`, `UNPAID` 변경
- 별도의 수동 전체 초기화 영역은 제거

## 8. 활동인증 동작

참가자 검색·표시·저장은 현재 사용자 경험을 유지한다.

- 검색 모집단: `student_roster` 전체
- `ALL`: 모든 활동인증 게시판에서 검정 `#212429`
- 현재 게시판과 일치하는 `ONCE`: 검정 `#212429`
- 납부 행 없음 또는 다른 게시판 `ONCE`: 회색 `#8A919C`
- 검정과 회색 모두 선택 가능
- 게시글 메타데이터는 기존 키 `participant_dues_payer_ids`를 유지해 마이그레이션 호환성을 지킨다.

## 9. 오류 처리와 원자성

- 원우회비 업로드는 전체 파일 검증 후에만 기존 납부 행을 삭제한다.
- 삽입이나 감사 로그 커밋이 실패하면 삭제를 포함한 전체 작업을 롤백한다.
- 명부 업로드 중 동시 변경이 발생하면 전체 롤백하고 재시도를 안내한다.
- 납부 수정 대상 명부 행이 없거나 `ONCE` 게시판이 유효하지 않으면 정규화된 404/422 오류를 반환한다.
- 원본 엑셀과 행별 PII는 운영 감사 로그에 저장하지 않는다.

## 10. 검증

백엔드:

- 빈 DB Alembic 업그레이드와 기존 `0028` 데이터 이관
- 업그레이드·다운그레이드 왕복 시 명부/ALL/ONCE 건수 보존
- 명부 신규 insert, 기존 overwrite, 누락 행 유지, 납부 상태 보존
- 납부 업로드 성공 시 기존 `ALL`과 `ONCE` 전부 교체
- 납부 파일 불일치 시 기존 납부 상태와 감사 로그 무변경
- 개별 `ALL`/`ONCE`/`UNPAID`, 권한, 유효 게시판 검사
- 활동인증 검색과 미납 참가자 저장 회귀

프론트엔드:

- 관리자 메뉴에 `원우 명부`와 `원우회비`가 각각 존재
- 원우 명부 테이블에 납부 용어와 수정 버튼이 없음
- 이름·학번·전공 검색 및 100명 페이지네이션
- 원우회비 업로드 경고와 전체 교체 요약
- 납부 편집기에서 신원 읽기 전용 및 세 상태 변경
- 활동인증 검정/회색 표시와 양쪽 선택 가능 회귀

실제 화면 QA:

- 대량 명부 테이블 데스크톱·좁은 화면 가독성
- 현재 납부 업로드 전후 건수와 목록 교체
- `ALL`, 일치 `ONCE`, 불일치 `ONCE`, 미납의 색상 및 선택 결과 캡처

## 11. 범위 제외

- 학기별 납부 이력 조회와 복원
- 과거 엑셀 파일 보관
- 원우 명부 행 삭제
- 회원 계정과 원우 명부 자동 연결
- 한 원우의 여러 `ONCE` 게시판 동시 보유
