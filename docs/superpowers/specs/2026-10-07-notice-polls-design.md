# 공지사항 투표 설계안

작성일: 2026-10-07 · 상태: “구현”으로 승인, 구현 및 로컬 검증 진행

작업 연결: WP6 공지사항 / WP8 관리자 / WP9 통합. `PLAN.md`의 투표는
P2 항목이며, 이번 사용자의 명시적 요청으로 이 기능의 설계를 진행한다.
기존 Expo Router, FastAPI, PostgreSQL과 공지사항 구조를 유지한다.

## 1. 사용자 요구와 레퍼런스

확정된 요구:

- 카카오톡 투표의 생성, 참여, 재투표, 집계와 결과 확인 흐름을 구현한다.
- 투표는 공지사항 글에만 붙인다. 별도 투표 게시판이나 관리자 메뉴를 만들지 않는다.
- 생성, 질문·항목·옵션 설정, 수정과 종료는 관리자만 할 수 있다.
- 투표 참여자는 누가 어떤 항목을 선택했는지 확인할 수 있다.
- 참여자 목록은 기존 원우회 사람 목록 카드의 디자인을 사용한다.
- 기존 공지 제목, 본문, 첨부파일, 고정, 분류와 원우회 활동내역 연동을 보존한다.

레퍼런스:

- [카카오 공식 2024-07-10 업데이트](https://pc.kakao.com/talk/notices/ko/2847?agent=win32):
  작성 화면에서 질문을 추가하고 최대 세 질문을 함께 제출하는 구성.
- [생성·옵션 화면 가이드](https://www.ajd.co.kr/contents/basic-tip/detail/카카오톡_카톡_투표_기능_생성부터_결과_확인까지-34602):
  텍스트·날짜, 항목 사진, 복수선택과 마감시간 설정을 참고한다.
- [참여·결과 화면 가이드](https://springit.tistory.com/215):
  선택, 투표하기, 항목별 집계, 다시 투표하기와 작성자 종료를 참고한다.
  이 자료의 화면은 2022년 기준이다.

카카오톡과의 제품 차이: 사용자 요구에 따라 기명 투표로 동작하며,
항목 추가·변경도 관리자 권한으로 처리한다. 익명 투표와 회원의 항목
추가는 이번 범위에 포함하지 않는다. 날짜·시간 허용 범위와 항목 개수는
아래 자체 기준을 적용하며, 카카오톡의 최신 제한과 같다고 주장하지 않는다.

## 2. 연결 방식

권장 방식은 공지 글의 자식 테이블에 투표를 저장하고, 기존 공지 저장
요청에 선택적인 `poll` 필드를 추가하는 것이다. 공지와 투표 설정은 같은
트랜잭션에서 검증하고 저장한다. 기존 클라이언트가 `poll`을 보내지 않으면
기존 투표를 유지한다.

대안인 별도 투표 게시글은 공지와 투표의 이동·권한·삭제가 분리된다.
`posts.metadata`에 투표자와 선택을 모두 넣는 방식은 동시 투표에서 덮어쓰기와
중복 집계 문제가 생긴다. 자식 테이블 방식은 기존 공지를 유지하면서 계정별
투표와 집계 제약을 데이터베이스에서도 보장할 수 있다.

## 3. 관리자 웹

기존 `/admin/boards`의 공지 작성·수정 폼에 `투표 추가` 영역을 붙인다.
공지 본문과 이미지·파일 설정은 지금과 같은 방식으로 사용한다.

설정 항목:

- 질문 제목, 텍스트 또는 날짜 유형.
- 선택항목 추가·삭제·순서 변경과 항목별 선택 이미지.
- 질문별 단일선택 또는 복수선택.
- 질문 추가·삭제. 한 공지에 1~3개 질문을 둔다.
- 투표 전체의 마감 날짜·시간. 달력과 시간 입력을 사용한다.
- 진행 중인 투표의 즉시 종료와 참여 인원·집계 확인.

초기 자체 기준은 질문마다 2~20개 항목, 질문 제목과 텍스트 항목 각각
100자이다. 날짜 항목은 날짜 선택기로 받고 같은 날짜를 중복 등록하지 않는다.
마감은 선택 사항이며 지정 시 현재보다 미래여야 한다. 화면은 한국 시간으로
표시하고 API와 저장은 기존 UTC 규칙을 따른다. 투표 마감은 공지 자체의
`deadline_at`과 별개이므로 한쪽을 수정해도 다른 값은 바뀌지 않는다.

관리자가 설정한 신규 투표는 공지 저장과 함께 등록한다. 입력·업로드·저장
실패 시 작성 내용을 유지한다. 투표 항목 이미지는 본문 갤러리에 중복 표시하지
않고 해당 항목 안에만 표시한다.

관리자 운영 기록에 투표 등록·설정 변경·종료를 남긴다. 기록 상세에는 공지·투표
ID와 질문 수 등만 넣고, 회원별 선택 명단이나 이름을 복제하지 않는다.

## 4. 회원 참여와 결과

기존 공지 상세의 본문·첨부 영역 다음에 투표 카드를 표시한다.

1. 질문과 항목, 단일·복수선택 표시, 종료 예정 시간을 확인한다.
2. 질문별 항목을 선택하고 하나의 `투표하기` 버튼으로 제출한다.
3. 질문이 여러 개이면 모든 질문에 답한 뒤 함께 제출한다.
4. 성공한 서버 응답 후 내 선택, 항목별 득표 수·막대, 전체 참여 인원을 표시한다.
5. 진행 중이면 `다시 투표하기`로 기존 선택을 불러와 변경한다.
6. 결과의 `참여자 보기`에서 전체 참여자의 선택을 확인하고, 항목을 누르면
   그 항목을 선택한 참여자만 확인한다. 항목별 보기는 결과 화면의 세부 기능이다.
7. 종료되면 결과와 참여자 명단을 읽는 상태를 유지한다.

명단 열람 권한은 공지 열람 권한을 가진 로그인 회원으로 설정한다.
투표 참여자는 누구나 자신과 다른 참여자의 선택을 볼 수 있다.
결과 화면에 나오는 이름과 기수는 실제 투표 계정의 현재 공개 프로필이다.
원우 명부·회비 데이터는 투표 자격이나 명단 조회의 원천으로 사용하지 않는다.

참여자 목록은 기존 `frontend/app/(tabs)/board/[boardId].tsx`의 원우회
`cohortCard`와 같은 흰색 바탕, `#E1E4E9` 테두리, 10px 모서리와 기수 배지를
사용한다. 이름과 선택 항목을 오른쪽에 표시한다. 전체 보기에서는 복수선택의
모든 항목을 한 사람 카드에 나열하고, 항목별 보기에서는 같은 사람이 선택한
각 항목의 목록에 나타날 수 있다. 이메일, 전화번호, 소속과 회비 상태는 표시하지 않는다.

공통 카드 표현을 작은 컴포넌트로 추출하되 기존 원우회 목록의 데이터와
누르기 동작을 보존한다. 투표 버튼, 선택 상태와 결과 막대는 기존 파란색을 사용한다.
원우회 활동내역에 연동된 공지는 같은 공지 ID의 투표를 그대로 보여준다.

## 5. 권한·상태와 편집 규칙

- 투표가 있는 글의 최종 게시판은 반드시 `board_type = notice`여야 한다.
- 생성·설정 변경·종료에 `require_admin`을 사용한다. 회원은 직접 API를
  호출해도 투표 설정을 만들거나 바꿀 수 없다.
- 투표는 게시된, 읽을 수 있는 공지에서만 받는다. 비공개·숨김·삭제된 글과
  숨긴 게시판은 기존 글/게시판 읽기 규칙을 따른다.
- 관리자도 자신의 계정으로 회원과 같은 투표를 할 수 있다. 다른 계정의 표는
  대신 작성하거나 수정할 수 없다.
- 투표 시작은 공지가 게시된 시점이다. 종료는 `closed_at`이 있거나
  `ends_at <= 현재 UTC 시각`인 경우이며 백엔드에서 매 요청마다 검사한다.
- 종료 후 제출·재투표는 거절한다. 종료 상태를 다시 여는 기능은 이번 설계에 없다.
- 재투표는 기존 선택을 한 트랜잭션에서 교체한다. 반복된 동일 요청은 중복 표를 만들지 않는다.
- 첫 참여 전에는 질문·항목을 자유롭게 수정하거나 투표를 제거할 수 있다.
- 참여가 생기면 질문 제목·유형, 항목 문구·이미지·순서와 단일/복수 설정을
  고정한다. 관리자는 공지 본문 수정, 진행 중 마감 조정과 종료를 할 수 있다.
  표가 있는 투표 제거·구조 변경은 `409 POLL_HAS_VOTES`로 거절한다.
- 최초 참여 시 `first_voted_at`을 기록한다. 이후 참여자가 모두 탈퇴해도
  이 값으로 구조 고정을 유지하고, 과거 투표를 새 투표처럼 바꾸지 않는다.
- 종료된 투표의 마감을 미래로 바꿔 자동 재개하지 않는다.
- 투표가 붙은 공지는 다른 공지 게시판으로 이동할 수 있지만 일반 게시판으로
  옮기는 요청은 거절한다. 기존 공지 기능의 이동·권한 검증을 함께 적용한다.

첫 참여 후 구조 고정, 질문·항목 한도, 명단 열람 대상과 탈퇴 시 표 삭제는
이번 설계의 초기 동작 결정이다. 이후 사용자가 변경할 수 있도록 규칙을
투표 도메인에 모으고 기존 게시판·계정 정책과 섞지 않는다.

## 6. 데이터·API 제안

Alembic으로 다음 정규화 테이블을 추가한다. 기존 공지는 새 행을 만들지 않는다.

| 테이블 | 주요 값과 제약 |
| --- | --- |
| `post_polls` | `post_id` 유일, `ends_at`, `closed_at`, `first_voted_at`, `revision`, 생성·수정 시간 |
| `poll_questions` | 투표 FK, 제목, `text/date`, 복수선택 여부, 순서 |
| `poll_options` | 질문 FK, 텍스트/날짜 값, 선택 이미지 FK, 순서 |
| `poll_ballots` | 투표 FK, 사용자 FK, 최초·최종 제출 시간, 투표+사용자 유일 |
| `poll_selections` | 투표용지 FK, 항목 FK, 투표용지+항목 유일 |

다른 투표/질문의 항목을 섞거나 단일선택에 여러 항목을 제출하는 요청은 거절한다.
표 수·참여 인원은 선택과 투표용지에서 집계하고 별도 중복 카운트를 저장하지 않는다.
계정과 선택의 연결은 서버가 인증한 사용자 ID로만 만든다. 탈퇴 시 해당 계정의
투표용지·선택을 삭제하고 집계를 갱신한다. 이름·기수 스냅샷은 별도로 복제하지 않는다.

API 초안:

| 요청 | 동작 |
| --- | --- |
| 기존 공지 POST/PUT + 선택적 `poll` | 관리자만 공지와 설정을 원자적으로 저장. 생략 시 기존 투표 유지, 명시적 null은 제거 규칙 적용 |
| `GET /posts/{post_id}/poll` | 읽기 권한 검증 후 질문·내 선택·집계·종료 상태·revision 반환 |
| `PUT /posts/{post_id}/poll/vote` | 로그인 계정의 모든 질문 답변을 검증하고 제출/교체 |
| `GET /posts/{post_id}/poll/participants` | 페이지 단위 참여자와 선택 반환. 선택적 `option_id` 필터 |
| `POST /posts/{post_id}/poll/close` | 관리자 즉시 종료. 반복 종료는 같은 종료 상태 반환 |

응답은 기존 `{status, data}` 및 오류 `{status, message, code}` 규칙을 따른다.
참여자 API는 기존 페이지 규칙을 사용하고 `option_id`가 같은 투표에 속하는지도
검증한다. 참가자 응답은 계정 ID, 공개 이름·기수와 선택 항목만 포함한다.

공지 수정, 투표 제출과 종료는 같은 투표 잠금 순서를 사용한다. 설정 수정은
`revision`을 검사해 오래 열린 편집기의 덮어쓰기를 `409 POLL_CHANGED`로 막는다.
회원 제출도 화면에서 받은 `revision`과 질문별 `option_ids`를 보내며, 버전이
다르면 최신 질문을 다시 확인하도록 같은 오류를 반환한다. 일반 투표·재투표는
설정 revision을 올리지 않는다.
제출 중 마감·숨김·삭제가 바뀌는 경우도 트랜잭션 안에서 재확인한다.

항목 사진은 기존 준비 완료된 보호 미디어만 사용한다. 미디어 읽기 권한과
계정 탈퇴 시 첨부 보존 판단에 투표 항목 연결을 추가한다. 소유자가 탈퇴해도
공지에 연결된 항목 사진은 남고, 회원에게는 공지 권한 확인 후 서명 URL을 제공한다.
관리자 사진 변경·해제는 기존 미디어 보존 정책을 따르며 원본을 즉시 삭제하지 않는다.

## 7. 변경 지점과 확인 기준

주요 변경 지점은 새 투표 모델·스키마·도메인/라우터·Alembic, 공지 create/update
연결, 미디어 권한/탈퇴 처리, 관리자 NoticeForm과 저장·편집 상태, 공통 공지 작성·수정
경로, 회원 공지 상세, API 클라이언트/타입과 참여자 카드이다. 새 회원 화면 경로는
만들지 않고 공지 상세 안의 결과·참여자 패널을 사용한다.

구현 시 API/DB/권한/프론트 계약 파일과 WP6/WP8/WP9 기록을 함께 갱신한다.
투표 캐시는 계정별로 구분하고 로그아웃·계정 전환 시 기존 정리 규칙을 따른다.
성공한 제출·설정 변경·종료 뒤 투표와 공지 상세 캐시를 갱신한다.

필수 검증:

- 관리자 생성·수정·종료 성공, 회원의 같은 요청 거절, 일반 게시판 투표 거절.
- 텍스트·날짜·사진·여러 질문·단일/복수선택과 전체 답변 제출.
- 중복 클릭, 같은 제출 재시도, 재투표와 집계의 계정별 유일성.
- 마감 경계, 수동 종료, 비공개/숨김/삭제와 직접 API 접근.
- 첫 표 이후 구조 수정 거절, 공지 본문 수정 시 투표·첨부·고정·분류 보존.
- 전체·항목별 명단과 공개 프로필, 다른 투표 항목 필터 거절, 페이지 처리.
- 동시 제출/설정 변경/종료, 오래 열린 편집기와 계정 전환 캐시.
- 회원 탈퇴 후 표 삭제, 연결된 투표 이미지 보존과 서명 미디어 권한.
- Alembic 적용/되돌리기와 기존 데이터 보존, backend 검사, frontend typecheck.
- 실제 관리자 웹에서 공지 등록 → 회원 참여 → 재투표 → 결과/명단 → 관리자 종료.

구현 보완: `poll: null` 제거 요청은 글 저장의 `poll_revision`에 편집기에서
불러온 버전을 함께 보내야 한다. 오래된 제거도 `409 POLL_CHANGED`로 거절한다.
투표가 있는 게시판의 유형을 일반 게시판으로 바꾸는 요청도 거절한다.

게시판 배타 잠금 아래에서 기존 투표를 확인한다.
